# Existing users in the create-user flow

Administrators and superusers can open **Users → Create User**, enter an email and select the target organization. A normalized, exact-email check runs after 350 ms. If the account exists, the modal identifies it and offers **Assign Existing User** with an organization-specific role. Name/password/profile fields are hidden; they are not submitted or updated for an existing account. If the account does not exist, the normal new-user form remains available.

A user can belong to multiple organizations. Assignment adds an `organization_users` membership and preserves the existing account, password, global roles, primary organization and other memberships. Only a user without any primary organization receives the new organization as their primary. Existing assignment is reported explicitly and repeated/concurrent requests do not create duplicate memberships or overwrite roles. Inactive memberships can be reactivated with their previous role; suspended/inactive accounts cannot be assigned here. This path does not send invitations or generate password-reset tokens.

The existing-user role applies only to the selected organization. Supported presets are administrator, end user, accountant and inventory manager. Superuser/global/custom roles cannot be assigned through this path. Non-superusers can assign only within their authenticated organization. Lookup and assignment routes require `users.create` authorization and an administrator/superuser role.

`POST /api/v1/users/lookup-email` accepts `email` and `organizationId`, returning a minimal identity and membership state for that organization. Other memberships and private profile/credential fields are not returned. `POST /api/v1/users/assign-existing` accepts `userId`, `email`, `organizationId` and `roleId`; it rechecks identity, account availability, organization and role, then writes transactionally under a user row lock. No schema migration is required.

Email/organization changes clear suggestions and cancel pending requests immediately. Closing/reopening the dialog cancels old checks; failed checks can be retried. A duplicate-email conflict during new-user creation triggers another lookup instead of silently assigning access. Assignment always requires an explicit user action.

Organization-scoped user lists include active secondary memberships and display their scoped role. Explicitly inactive memberships override legacy primary-organization fallback. Shared accounts expose only the identity/status fields needed for the list, and account-wide edit/delete actions remain restricted to the primary organization or a superuser. Organization memberships can be managed from the existing organization-management flow.

Verification: 55 focused user-creation, assignment, invitation and organization-access tests pass, plus the isolated MySQL integration test. MySQL checks cover three memberships on one account, one primary, unchanged credentials/global roles, simultaneous duplicate assignment and organization-scoped listing. Client production and API TypeScript builds pass; the client retains its initial-bundle budget warning. Browser verification uses the production client with a synthetic local API: suggestion, role selection, assignment, already-assigned state and the same account assigned to a second organization. No production accounts were changed and no email was sent.
